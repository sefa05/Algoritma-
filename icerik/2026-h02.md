## PZT · Ana dizi: Hibrit arama ve reranker (09:00)

```
1/ Anlamsal arama (embedding) RAG'in varsayılanı oldu.

Ama tek başına kullanıldığında belirli soru tiplerinde sistematik olarak ıskalıyor. Nedeni ve çözümü:
```
```
2/ Embedding anlamı yakalar, tam eşleşmeyi değil.

Ürün kodu (XR-2041), fatura numarası, kişi adı ya da kısaltma içeren sorgularda anlamca "benzer" ama yanlış belgeyi getirebilir.
```
```
3/ Anahtar kelime araması (BM25) tersini yapar: tam terimi kaçırmaz, ama eş anlamlıyı bilmez.

"İade" diye aranınca yalnızca "geri gönderim" geçen belgeyi bulamaz.
```
```
4/ Hibrit arama ikisini birlikte çalıştırıp sonuçları birleştirir.

Yaygın yöntem Reciprocal Rank Fusion (RRF): her belgeye iki listedeki sırasına göre puan verir. Farklı skor ölçeklerini eşitlemeye gerek kalmaz.
```
```
5/ Reranker ikinci aşamadır.

İlk aşamanın getirdiği adayları (örneğin 50 parça) soruyla birlikte okuyan bir model yeniden sıralar. Daha yavaş ama daha isabetli. Bu yüzden yalnızca aday kümesine uygulanır.
```
```
6/ Sıra: hibrit arama → reranker → ilk 5–10 parça modele.

Hangi adımın işe yaradığını görmek için retrieval'ı ayrıca ölçün: doğru parça ilk k sonuç içinde mi?
```
**İlk yanıt (kaynak):**
```
RRF'nin kaynağı: Cormack, Clarke ve Büttcher, "Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods" (SIGIR 2009).
```

## SAL · Teknik not: RAG'i iki ayrı skorla ölçmek (21:00)

```
RAG kalitesini tek bir skorla ölçmeyin. İki ayrı soru var:

1) Retrieval: doğru parça ilk k sonuçta mı? (recall@k)
2) Üretim: doğru parça geldiğinde cevap doğru mu?

Yalnızca son cevaba bakarsanız hangi katmanın bozuk olduğunu bilemezsiniz.
```
**İlk yanıt:**
```
Pratik: değerlendirme setindeki her soru için doğru cevabın bulunduğu parçayı (ya da belgeyi) işaretleyin.

Böylece retrieval'ı LLM çağırmadan, saniyeler içinde ve çok düşük maliyetle ölçebilirsiniz.
```

## ÇAR · Dizi: Değerlendirme seti nasıl kurulur (21:00)

```
1/ Bir LLM sistemi için değerlendirme seti nasıl kurulur? 6 adım 🧵
```
```
2/ Gerçek girdiden başlayın.

Destek kayıtları, e-postalar, kullanıcı soruları. Kendi yazdığınız örnekler genelde sistemin zaten iyi olduğu durumları temsil eder.
```
```
3/ Zor örnekleri bilerek ekleyin.

İki konulu, yazım hatalı, eksik bilgili ve cevabı belgelerde olmayan sorular. Kolay örnekler her sistemi iyi gösterir.
```
```
4/ Doğru cevabı, işi bugün yapan kişiyle birlikte yazın.

Mühendisin "doğru" sandığı ile operasyon ekibinin doğru kabul ettiği cevap ayrışabilir.
```
```
5/ Puanlama yöntemini baştan seçin:

• Sınıflandırma: tam eşleşme
• Format ve zorunlu alanlar: kural kontrolü
• Serbest metin: insan ya da kalibre edilmiş bir LLM hakem
```
```
6/ Kategori bazında raporlayın.

Genel doğruluk, kritik bir kategorideki düşüşü gizleyebilir.
```
```
7/ Seti dondurun ve sürümleyin.

Her istem, model ya da retrieval değişikliğinden sonra aynı seti çalıştırın. Skor düştüyse değişiklik geri alınır.
```

## CUM · Mit mi gerçek mi: Uzun bağlam ve RAG (21:00)

```
Mit: "Bağlam penceresi 1M token'a çıktı, RAG'e gerek kalmadı."

Kısmen. Küçük ve sabit bir belge seti pencereye sığıyorsa, önbellekli uzun bağlam RAG'den daha basit bir çözüm olabilir.

Ama her soruda 1M token göndermek maliyet, gecikme ve doğruluk sorunu doğurur.
```
**İlk yanıt (hesap):**
```
Hesap: Claude Opus 5.5'te 1M girdi token'ı $4. Her soruda tüm bağlamı göndermek soru başına yaklaşık $4, önbellekten okunursa yaklaşık $0,20.

```
**İkinci yanıt (kaynak):**
```
Ayrıca uzun bağlamda bilginin konumu sonucu etkileyebiliyor. Kaynak: Liu vd., "Lost in the Middle: How Language Models Use Long Contexts" (TACL 2024).

Yeni modellerde etki azalmış olabilir, kendi verinizle test edin.
```
