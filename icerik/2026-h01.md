```
1/ Bir LLM sistemi demoda çalışıp üretimde neden bozulur?

Kurduğum ve incelediğim sistemlerde sorun nadiren modelin kendisi oluyor. Kırılma noktaları genelde başka yerde.

Altı tanesi:
```
✏️ "Kurduğum ve incelediğim sistemlerde" ifadesi senin deneyimine dayanıyor. Uymuyorsa "Sorun nadiren modelin kendisi oluyor" diye başla.

```
2/ Retrieval

RAG'de yanlış cevap gördüğünüzde önce şuna bakın: doğru belge parçası modele hiç ulaştı mı?

Ulaşmadıysa istemi değiştirmek boşuna. Sorun arama katmanında.
```
```
3/ Ölçüm seti yok

Doğru cevaplarıyla 50–100 gerçek örnek yoksa her değişiklik bir tahmindir.

İstemi "iyileştirirken" başka bir yeri bozduğunuzu fark etmezsiniz.
```
```
4/ Bileşik hata

Her adımı %95 doğru çalışan 5 adımlı bir ajan akışı, uçtan uca yaklaşık %77 doğrulukla çalışır (0,95⁵ ≈ 0,77, adımlar bağımsızsa).

Adım sayısı, model kalitesi kadar önemli.
```
```
5/ Gerçek girdi demo girdisine benzemez

Kullanıcı yazım hatasıyla, iki konuyu tek mesajda, eksik bilgiyle yazar.

Test seti temiz örneklerden oluşuyorsa üretimdeki başarıyı olduğundan yüksek ölçersiniz.
```
```
6/ Dolaylı istem enjeksiyonu

Ajanın okuduğu bir e-posta ya da belge, içine gömülü bir talimat taşıyabilir. Model bunu kullanıcının isteği sanabilir.

```
```
7/ Yanlış maliyet ölçüsü

İki kat deneme gerektiren ucuz model ucuz değildir.
```

## SAL · Teknik not: Prompt caching (21:00)

```
Her istekte aynı uzun bağlamı (ürün kataloğu, politika belgesi, uzun sistem istemi) gönderiyorsanız prompt caching'e bakın.

Claude Opus 5.5'te 1M girdi token'ı $4. Aynı token önbellekten okunduğunda $0,20.

Şart: önbelleğe alınan kısım her istekte birebir aynı olmalı.
```
**İlk yanıt:**
```
Sık yapılan hata: sistem isteminin başına tarih, saat ya da kullanıcı adı koymak.

Önbellek önek eşleşmesiyle çalışır. Baştaki tek bir değişiklik, sonrasının tamamını geçersiz kılar. Değişen bilgiyi sona koyun.
```
**İkinci yanıt (kaynak):**
```
Not: önbelleğe ilk yazma, normal girdiden biraz daha pahalı. Kazanç, aynı önek tekrar tekrar okundukça çıkar.

Kaynak: Anthropic, prompt caching dokümantasyonu ve fiyat listesi (Eylül 2026).
```

## ÇAR · Dizi: RAG teşhis sırası (21:00)

```
1/ RAG sistemi yanlış cevap verdiğinde çoğu ekip ilk iş istemi değiştiriyor.

Oysa istem genelde en son bakılması gereken yer. Teşhis sırası:
```
```
2/ Cevap indekste var mı?

Belge hiç yüklenmemiş, eski sürümü yüklenmiş ya da PDF'ten metin çıkarılamamış olabilir. Taranmış belgelerde bu sık görülür.
```
```
3/ Arama onu getirdi mi?

Doğru parça ilk k sonuç içinde mi? Değilse anlamsal aramayı anahtar kelime aramasıyla (BM25) birleştirin, sonuçları bir reranker ile yeniden sıralayın.
```
```
4/ Parçalama cevabı böldü mü?

Cevap iki parçaya bölünmüşse model yarısını görür. Belgeyi yapısına göre (başlık, madde, tablo) parçalayın, parçalar arasında örtüşme bırakın.
```
```
5/ Model bağlamı kullandı mı?

Doğru parça geldiği hâlde cevap yanlışsa: "yalnızca verilen belgelere dayan, cevap yoksa söyle" talimatını verin, cevabın hangi parçadan geldiğini göstermeyi zorunlu kılın.
```
```
6/ Bu sırayla bakmazsanız, arama katmanındaki bir hatayı istem yazarak kapatmaya çalışırsınız.

Bu da genellikle bir yeri düzeltirken başka bir yeri bozar.
```
